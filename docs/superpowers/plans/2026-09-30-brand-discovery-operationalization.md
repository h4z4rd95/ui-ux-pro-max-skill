# سند عملیاتی‌سازی پلتفرم Brand Discovery Wizard

> این سند برای **ایجنت دیگری** نوشته شده که قرار است این پروژه را اجرا/گسترش دهد.
> زبان تعامل با کاربر: **فارسی (rtl)**. خروجی نهایی: **یک پرامت مستر، بدون API و بدون هوش مصنوعی.**

---

## ۰. مفهوم اصلی (چرا این روش کار می‌کند)

سه مشکل همیشگی در سفارش طراحی سایت توسط ایجنت کدنویس وجود دارد:

1. **ذهنیت کاربر و AI یکی نیست** — کاربر می‌گوید «مدرن و شیک»، AI از آن یک قالب بوت‌استرپ می‌سازد.
2. **کلمات مبهم هستند** — «اسلاید نرم»، «لودینگ خوشگل»، «کمی سه‌بعدی» هیچ معنای دقیقی ندارند.
3. **گزینه‌ها توضیح ندارند** — کاربر نمی‌داند انتخابش چه پیامدی دارد، تا وقتی که دیر شده.

راه‌حل این پروژه سه‌لایه است:

```
Layer 1  Pre-designed Elements   → هر گزینه یک نمونه بصری واقعی (SVG) دارد
Layer 2  Metadata Triple         → هر گزینه می‌گوید: چه‌کار می‌کند / کِی استفاده شود / چه‌کار نمی‌کند
Layer 3  Real Reference          → هر گزینه یک رفرنس قابل جست‌وجوی واقعی دارد
```

**قانون طلایی:** هیچ گزینه‌ای بدون نمونه بصری + توضیح به کاربر عرضه نمی‌شود. تصویر، زبان مشترک کاربر و AI است.

## ۲. جریان کشف نیاز (Need-Discovery Flow)

ایجنت باید این ۷ مرحله را **به همین ترتیب** طی کند. هر مرحله قبل از رفتن به بعدی، باید حداقل یک پاسخ معتبر داشته باشد.

| # | مرحله | هدف | کلیدهای state |
|---|-------|-----|---------------|
| ۱ | **محصول** | نوع سایت (کامل / لندینگ / اپلیکیشن) | `productMode`, `productType` |
| ۲ | **استک** | خانواده‌ی تکنولوژی | `stackFamilies` |
| ۳ | **استایل** | سبک بصری (از ۷۶ دسته) | `styleChoices` |
| ۴ | **برند** | نام، لحن، کاراکتر/ماسکوت | `brandName`, `brandTone`, `needsMascot`, `mascotStyle` |
| ۵ | **موشن** | لودینگ، اسکرول، اسلایدر، ۳D | `wantsLoader`, `loaderType`, `smoothScroll`, `sliderMode`, `motionLevel`, `threeDLevel` |
| ۶ | **محتوا** | صفحات/سکشن‌ها + یکپارچگی استایل | `contentSections`, `pageStyleConsistency`, `notes` |
| ۷ | **خروجی** | تحویل پرانت مستر | `derived.prompt` |

### ۲.۱ موتور سوالات شاخه‌ای (Branching)

`getVisibleQuestions(state)` در `brief-engine.js` فقط سوالاتی را برمی‌گرداند که **الان معنی دارند**. یعنی اگر کاربر لودینگ نخواست، سوال «نوع لودینگ» هرگز ظاهر نمی‌شود.

کلیدهایی که برمی‌گردد (باید با `QUESTION_LABELS` در `renderers.js` به فارسی ترجمه شوند — هرگز کلید خام kebab-case را به کاربر نشان ندهید):

| کلید خام | برچسب فارسی | شرط ظهور |
|----------|-------------|----------|
| `loader-type` | «نوع لودینگ» | `wantsLoader === true` |
| `mascot-style` | «سبک کاراکتر» | `needsMascot === true` |
| `three-d-objects` | «کدام آبجکت‌های سه‌بعدی» | `threeDLevel` غیر از none |
| `three-d-placement` | «سه‌بعدی کجا؟» | `threeDLevel` غیر از none |
| `hero-vs-slider` | «هیرو یا اسلایدر» | `sliderMode` مشخص نباشد |
| `page-style-consistency` | «یکنواختی استایل صفحات» | `productMode` فول‌سایت |
| `supportingPages` | «صفحات پشتیبان» | فول‌سایت |
| `landing-focus` | «تمرکز لندینگ» | حالت لندینگ |

## ۳. اسکریپت دقیق پرسش و پاسخ

ایجنت باید هر سوال را **همراه با نمونه بصری** بپرسد. الگوی استاندارد هر گزینه:

```
┌──────────────────────────────────────────────┐
│  [نمونه بصری ۱۱۲×۷۱]  │  عنوان گزینه          │
│                       │  ├── چه‌کار می‌کند      │
│                       │  ├── کِی استفاده شود   │
│                       │  ├── چه‌کار نمی‌کند      │
│                       │  └── رفرنس واقعی       │
└──────────────────────────────────────────────┘
```

این ساختار در `renderers.js` توسط `renderOptionCard()` و `renderVisualSelect()` پیاده شده.

### ۳.۱ سوالات مرحله‌ی محصول

- **«یک سایت کامل می‌خوای یا یک لندینگ پیج؟»** — دو کارت با `renderLayoutVisual`:
  - **فول‌سایت**: چند صفحه (Home/About/Pricing/Blog)، SEO، ناوبری عمیق. *کِی:* محصولی داریم که نیاز به اعتماد و توضیح دارد.
  - **لندینگ**: یک صفحه، یک مسیر تبدیل، اسکرول‌استوری. *کِی:* محصول واحد + یک CTA.
- بعد از انتخاب محصول، `productType` از **۱۶۱ محصول کاتالوگ** فیلتر می‌شود.
- **در حالت لندینگ حتماً سوال `landing-focus` پرسیده شود**: «روی چه چیزی مانور بدیم؟» (تبدیل/اعتماد/آموزش/حس فوریت).

### ۳.۲ سوالات مرحله‌ی استایل (مهم‌ترین بخش)

- از ۷۶ دسته‌ی استایل کاتالوگ، ابتدا `getStyleSuggestions(productType)` پیشنهاد می‌دهد.
- هر استایل در `visual-library.js` یک ورودی با ساختار زیر دارد:

```js
{
  title: "Glassmorphism",
  whatItDoes: "لایه‌های شفاف روی پس‌زمینه‌ی رنگی، حالت شیشه‌ای",
  useWhen: "محصول SaaS مدرن، مخاطب تکنیکال",
  doesNotDo: "متن طولانی و خواندنی؛ برای محتوای سنگین مناسب نیست",
  reference: "glassmorphism.com / apple.com",
  gradient: "rgba شفاف + blur"
}
```

- **۱۸ استایل دارای نمونه‌ی اختصاصی SVG هستن**: Minimalism, Neumorphism, Glassmorphism, Brutalism, 3D, Vibrant, Dark Mode, Claymorphism, Aurora, Retro-Futurism, Flat Design, Liquid Glass, Motion-Driven, Bento Box, Neubrutalism, AI-Native, Cyberpunk, Editorial.
- بقیه‌ی ۵۸ مورد توسط `pickStyleVisual(category)` با یک fallback meta تطبیق می‌شوند. **هرگز سوال بدون نمونه بصری نشان داده نشود.**

### ۳.۳ سوالات مرحله‌ی برند

- `brandName` — فیلد ساده.
- `brandTone` — کارت‌های چک‌باکس، هر کدام با description فارسی (دوستانه/رسمی/تکنیکال/بازیگوش/لوکس).
- **ماسکوت**: اول سوال باینری `needsMascot`، **اگر بله** آنگاه `mascot-style` ظاهر می‌شود (با `renderMascotVisual` — نمودهای صورت). یک `.option-hint` توضیح می‌دهد: «کاراکتر یعنی موجودی که در hero، states خالی و illustrations ظاهر می‌شود و برند را به یاد ماندنی می‌کند».
- **لوگو**: اگر کاربر لوگوی آماده دارد، در `notes` ذخیره می‌شود و در پرانت نهایی به عنوان «سبک رنگی باید با لوگو هماهنگ باشد» لحاظ می‌شود.

### ۳.۴ سوالات مرحله‌ی موشن (پرسش‌های دقیق از قبل پردازش‌شده)

این دقیقاً همان سوالاتی است که کاربر در درخواست اصلی‌اش مطرح کرد. هر کدام حالا یک نمونه بصری دارد:

| سوال | نمونه بصری | نکته |
|------|-----------|------|
| لودینگ می‌خوای؟ | — | باینری |
| **نوع لودینگ** | `renderLoaderVisual` (۴ پترن: اسپینر/پله/اسکلتن/پیشرفت) | فقط اگر `wantsLoader` |
| اسکرول نرم (Lenis-like) | chips + hint | توضیح: «اسکرول بین سکشن‌ها نرم می‌چسبد به جای پرش» |
| **اسلایدر یا هیرو؟** | `renderLayoutVisual` (دو لی‌اوت واقعی) | کلید `hero-vs-slider` |
| **میزان موشن** | `renderMotionVisual` (Low/Medium/High + SMIL انیمیشن) | جلوی over-animation را می‌گیرد |
| **میزان ۳D** | `renderThreeDVisual` (none/low/medium/high) | |
| **کدام آبجکت ۳D** | لیست با تصویر | فقط اگر ۳D روشن |
| **۳D کجا** | کل صفحه / فقط مودال‌ها و کاشی‌ها | کلید `three-d-placement` |

**تبصره‌ی مهم برای `three-d-placement`:** کاربر در درخواستش صراحتاً بین «قالب فول سه‌بعدی» و «قالبی که فقط مقداری از مودال‌ها/کاشی‌ها/سکشن‌ها سه‌بعدی باشند» تفاوت قائل شد. این دو گزینه باید دقیقاً با همین دو نمونه‌ی بصری متفاوت ارائه شود.

### ۳.۵ سوالات مرحله‌ی محتوا

- `contentSections` — چک‌باکس با توضیح هر سکشن (Hero / Features / Pricing / Testimonials / FAQ / CTA).
- **در فول‌سایت حتماً `page-style-consistency` پرسیده شود** (سه کارت، **فقط یکی قابل انتخاب**):
  - **مشابه سایت اصلی** — همه‌ی صفحات همان استایل hero را دارند.
  - **سازگار ولی متفاوت** — همان پالت/تایپو، اما لی‌اوت صفحه‌ای متفاوت.
  - **هر page شخصیت جدا** — مثل سايت‌های چندمنظوره.
- `notes` — متن آزاد کاربر، در پایان پرانت قرار می‌گیرد.

## ۴. کتابخانه‌ی المان‌های پیش‌طراحی‌شده (قلب پروژه)

فایل: `lib/visual-library.js`. **این مکانیزم همگرایی ذهنیت AI و کاربر است.**

### چرا SVG اینلاین؟

- بدون درخواست شبکه → سرعت بالا، آفلاین، بدون OTP/CDN
- قابل کنترل با CSS تم پروژه
- در پرانت نهایی به عنوان «الگوی طراحی» توصیف می‌شوند (نه فایل باینری)

### ساختار کلی توابع رندر

```js
renderSwatchVisual(swatch, uid)      // پالت رنگی (۳ تا ۵ رنگ)
renderMotionVisual(gradient, motion, uid)  // میزان حرکت + SMIL animate
renderThreeDVisual(shape, uid)       // شکل ۳D (کره/مکعب/توروس)
renderLoaderVisual(pattern, uid)     // ۴ پترن لودینگ انیمیشن‌دار
renderLayoutVisual(layout, uid)      # هیرو/اسلایدر/فول‌سایت/لندینگ
renderMascotVisual(face, uid)        # صورت کاراکتر
```

### قانون توسعه

وقتی یک گزینه‌ی جدید اضافه می‌شود، **سه قدم الزامی است**:

1. یک ورودی به `visual-library.js` اضافه کن با چهار فیلد: `whatItDoes` / `useWhen` / `doesNotDo` / `reference`.
2. اگر گزینه‌ی بصری است، یک نمونه‌ی SVG به آن اختصاص بده.
3. تست کن: `node --test tests/` — نباید خرابی‌ای در `getVisibleQuestions` بیاورد.

**خط قرمز:** گزینه‌ای که `doesNotDo` (چه‌کار نمی‌کند) نداشته باشد، رها نشده است. این فیلد است که از انتظارات غلط کاربر جلوگیری می‌کند.

## ۵. موتور پرانت (خروجی نهایی)

`generateMasterPrompt(state, ...)` در `brief-engine.js` یک **پرامت مستر تک‌قطعه‌ای** تولید می‌کند که شامل این بخش‌هاست:

```
1. Context        — نوع محصول، نوع سایت، استک انتخابی
2. Brand Identity — نام، لحن، پالت پیشنهادی، کاراکتر (اگر هست)
3. Visual Style   — استایل‌های انتخابی + whatItDoes هر کدام
4. Motion Spec    — لودینگ/اسکرول/اسلایدر/۳D با مقادیر نهایی
5. Page Strategy  — decidePageStrategy: لیست صفحات + سکشن‌ها
6. Content        — سکشن‌های انتخابی + یادداشت‌های کاربر
7. Constraints    — doesNotDoهای انتخاب‌ها (این بخش از انتظار غلط جلوگیری می‌کند)
8. Deliverables   — فایل‌های مورد انتظار + نحوه‌ی اجرا
```

`decidePageStrategy` بین دو مسیر انتخاب می‌کند:
- `FULL_SITE_PAGE_PRESETS` — صفحات استاندارد بر اساس نوع محصول
- `LANDING_SECTION_PRESETS` — سکشن‌های بر اساس `landing-focus`

ایجنت باید این موارد را تأیید کند:

- [ ] `.option-hint` برای هر گروه مبهم وجود دارد (اسکرول نرم، ماسکوت، لودینگ، یکپارچگی).
- [ ] پرانت نهایی شامل `doesNotDo`ها است.
- [ ] `node --test tests/` سبز است.
- [ ] سرور پیش‌نمایش روی `http://localhost:4173` در دسترس است.

## ۷. خطاهای متداول و راه‌حل

| مشکل | علت | راه‌حل |
|------|-----|--------|
| متن روی لیست سفید ناخوانا | `option` استایل نشده | `option { background: #1b1f27; color: var(--text) }` |
| کاربر می‌گوید «نگو اینو می‌خوام» | گزینه توضیح نداشت | اضافه کردن `whatItDoes` + `useWhen` |
| خروجی ایجنت کدنویس دور از سلیقه | نمونه بصری نبود | استفاده از `visual-library.js` |
| سوال بی‌ربط پرسیده شده | branching نادیده | چک `getVisibleQuestions` |
| Expectation mismatch بعد تحویل | `doesNotDo` در پرانت نبود | بخش Constraints را پر کن |

## ۸. دستورالعمل نهایی برای ایجنت اجراکننده

> **تو قرار نیست طراحی کنی.** تو قرار است **الگوی دقیق طراحی** را با کاربر قفل کنی.
>
> ۱. جریان ۷ مرحله‌ای را طی کن، با نمونه‌ی بصری برای هر گزینه.

> ۳. در پایان، پرانت مستر را تحویل بده.
> ۴. آن پرامت باید آن‌قدر دقیق باشد که ایجنت کدنویس **هیچ سوال دیگری** نپرسد.
>
> موفقیت یعنی: کاربر پرانت را می‌خواند و می‌گوید «بله، همینو می‌خواستم».
